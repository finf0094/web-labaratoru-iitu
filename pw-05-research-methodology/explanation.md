# Как защищать ПР5 — шпаргалка

## 1. Суть за 30 секунд

> «Тема ПР5 — инструменты (tools) для LLM-агентов: как подключать их к AI-платформе. Есть два способа: нативно в LangChain через декоратор `@tool` или через отдельный MCP-сервер, который любой агент подключает по стандартному протоколу. Я сравниваю их по четырём вопросам: сколько времени тратит разработчик, когда те же инструменты нужны в двух приложениях; насколько точно агент выбирает нужный инструмент (и что будет, если инструментов 20, а не 5); какую задержку добавляет MCP; насколько это удобно разработчикам. Дизайн — смешанный, в основном количественный: эксперимент с 24 разработчиками (каждый пробует оба способа), 120 тестовых задач для агента, замер задержки и короткие интервью».

## 2. Основные понятия простыми словами

* **Tool (инструмент)** — обычная функция, которую модель может «попросить» выполнить: `get_timetable(group, date)`, `create_ticket(...)`. У инструмента есть имя, описание и JSON-схема аргументов.
* **Function calling / tool calling** — модели передают список инструментов, и она вместо текста может вернуть структурированный вызов: «вызови `get_timetable` с `group="SE-2203"`». Сам код выполняет **приложение**, а не модель.
* **Agent loop (цикл агента)** — LLM решает, что делать → приложение вызывает инструмент → результат возвращается в LLM → LLM продолжает или даёт финальный ответ. Повторяется, пока задача не решена (идея ReAct, Yao et al. 2023).
* **MCP (Model Context Protocol)** — открытый стандарт (Anthropic, 2024), «USB-порт для AI»: инструмент пишется один раз как MCP-сервер и подключается к любому совместимому приложению.
  * **Host** — приложение с LLM (наша платформа, чат, IDE).
  * **Client** — часть host, которая держит соединение с одним сервером.
  * **Server** — программа, которая предоставляет возможности:
    * **tools** — функции, которые модель может вызвать;
    * **resources** — данные только для чтения (файлы, записи);
    * **prompts** — готовые шаблоны запросов.
  * **Транспорты:** **stdio** — сервер запускается как локальный подпроцесс, общение через стандартный ввод/вывод (быстро, только на этой машине); **streamable HTTP** — сервер работает как сетевой сервис по URL (можно один сервер на всю организацию). Сообщения — JSON-RPC.
* **LangChain** — Python-фреймворк для LLM-приложений: модели, инструменты, агенты. **LangGraph** — его «движок» для агентов: агент как граф шагов с состоянием (в LangChain 1.0 функция `create_agent` строится на LangGraph).
* **`@tool`** — декоратор LangChain: превращает Python-функцию в инструмент (имя и схема берутся из сигнатуры, описание — из docstring). Инструмент живёт **внутри** процесса агента.
* **`langchain-mcp-adapters`** — библиотека-мост: `MultiServerMCPClient` подключается к одному или нескольким MCP-серверам и превращает их tools в обычные LangChain-инструменты.
* **Другие библиотеки:** `mcp` — официальный Python SDK для MCP-серверов/клиентов; **FastAPI** — мок-сервисы с синтетическими данными (расписание, заявки); **pytest** — приёмочные тесты («готово» = все тесты зелёные).
* **OpenAI-compatible API** — модель за агентом подключается по стандартному API, поэтому это может быть облачная модель или своя open-weight модель через **vLLM** или **Ollama**. Модель у нас — фиксированный параметр, а не предмет исследования.
* **RAG** — вне рамок ПР5 (это тема ПР6).

## 3. Мини-пример кода (иллюстрация, не часть эксперимента)

MCP-сервер с одним инструментом (`mcp` SDK v2 — в нём `FastMCP` переименован в `MCPServer`):

```python
# timetable_server.py
from mcp.server.mcpserver import MCPServer

server = MCPServer("timetable")

@server.tool()
def get_timetable(group: str, date: str) -> list[dict]:
    """Return the classes of a student group on a date (YYYY-MM-DD)."""
    return [{"time": "09:00", "course": "Research Methods", "room": "305"}]

if __name__ == "__main__":
    server.run("stdio")          # или server.run("streamable-http")
```

Загрузка этого сервера в LangChain/LangGraph-агента:

```python
import asyncio
from langchain_mcp_adapters.client import MultiServerMCPClient
from langchain.agents import create_agent
from langchain_openai import ChatOpenAI

async def main():
    client = MultiServerMCPClient({
        "timetable": {"command": "python", "args": ["timetable_server.py"], "transport": "stdio"},
        # "timetable": {"url": "http://localhost:8000/mcp", "transport": "streamable_http"},
    })
    tools = await client.get_tools()                     # MCP tools -> LangChain tools
    model = ChatOpenAI(model="my-model", base_url="http://localhost:8000/v1")  # облако или vLLM/Ollama
    agent = create_agent(model, tools)
    result = await agent.ainvoke({"messages": [("user", "Timetable of SE-2203 on 2027-03-03?")]})
    print(result["messages"][-1].content)

asyncio.run(main())
```

Нативный вариант — та же функция с `@tool` (`from langchain_core.tools import tool`) прямо в коде агента, без сервера. **Важно:** API этих библиотек часто меняются между версиями, поэтому в исследовании версии фиксируются.

## 4. Вопросы и гипотезы (выучить)

| RQ | О чём | Гипотеза | Чем проверяю |
|---|---|---|---|
| RQ1 трудозатраты | Те же 3 инструмента нужны в двух приложениях: MCP vs `@tool` | MCP экономит ≥ 25 % общего времени | Парный t-test (или Wilcoxon), 24 разработчика |
| RQ2 надёжность | Точность вызова (правильный tool + правильные аргументы); 5 vs 20 инструментов | H2a: MCP и native эквивалентны (±5 п.п.); H2b: при 20 инструментах точность ниже ≥ 10 п.п. | Bootstrap CI разности; McNemar, 120 задач × 3 прогона |
| RQ3 накладные расходы | Задержка вызова: in-process vs MCP stdio vs MCP HTTP | Медиана < 10 мс (stdio), < 30 мс (HTTP), < 2 % времени шага агента | Медиана, p95, bootstrap CI, 1000 вызовов |
| RQ4 удобство | Как разработчики оценивают MCP | SUS ≥ 68 и не ниже, чем у native | SUS, TAM, интервью |

## 5. Как обосновать каждое решение

* **Откуда вопросы?** Пробелы в литературе: польза MCP («написал раз — используешь везде») заявлена, но не измерена (Anthropic 2024; Hou et al.); бенчмарки MCP (MCP-Universe, MCP-Bench) оценивают модели, а не способ подключения; накладные расходы протокола и удобство для разработчиков не измерены.
* **Почему mixed methods, в основном количественный?** RQ1–RQ3 — причинно-следственные вопросы («уменьшает ли», «добавляет ли») → нужен эксперимент и статистика. Но цифры не объясняют «почему» → короткие интервью и think-aloud. Дизайн *explanatory sequential* (QUAN → qual), Creswell.
* **Тип исследования по лекции (Kothari):** applied, empirical, analytical, mixed, decision-oriented; подходы — experimental (меняем способ подключения и число инструментов), simulation (мок-сервисы с синтетическими данными), inferential (выводы о разработчиках по выборке).
* **Почему within-subjects (каждый пробует оба способа)?** Навыки людей сильно различаются; когда человек сам себе контроль, этот разброс убирается и нужно меньше участников. Эффект обучения убираем **контрбалансировкой (Latin square)**: половина начинает с MCP, половина с native, и есть два равноценных набора инструментов (A и B), чтобы никто не делал одно и то же дважды.
* **Валидность:** одинаковые задачи, тесты, модель и промпты в обоих условиях; «готово» определяют тесты, а не мнение; стандартные шкалы SUS/TAM; две модели и два набора инструментов; триангуляция с интервью.
* **Надёжность:** фиксированные версии библиотек и моделей, temperature 0, 3 прогона, автоматические замеры, двойное кодирование 20 % интервью, проверка авто-разметки людьми (κ ≥ 0.8), Cronbach's α.
* **Выполнимость:** только open-source, мок-сервисы, один компьютерный класс, ~2 часа на участника.
* **Этика:** информированное согласие, добровольность (можно выйти в любой момент, не влияет на оценки), анонимность (коды P01…), безопасное хранение, удаление записей после кодирования, закон РК о персональных данных; инструменты работают только с синтетическими данными.

## 6. Вероятные вопросы на защите

| Вопрос | Ответ |
|---|---|
| Почему 24 разработчика? | Power analysis для парного t-test: α = 0.05, мощность 0.8, ожидаемый эффект d = 0.6 → 24 (d = 0.5 → 34, d = 0.8 → 15). 24 делится на 4 группы Latin square; набираем 28 с запасом ~15 % на выбывание, при возможности 36. Считает `tools/sample_size.py`. |
| Почему 120 задач? | Для McNemar (5 vs 20 инструментов, падение 90 % → 80 %, discordant 12 % и 2 %) нужно 108 задач; берём 120 с запасом 10 % на задачи, отброшенные после пилота. 120 × 3 = 360 попыток дают для разницы MCP − native доверительный интервал ±3.3 п.п. — меньше порога эквивалентности 5 п.п. |
| Зачем 3 прогона? | Ответы модели могут отличаться даже при одинаковом запросе; 3 прогона показывают стабильность (pass^3, как в τ-bench). |
| Зачем 1000 замеров задержки? | Для p95 нужно достаточно «хвостовых» значений: 1000 вызовов → 50 выше p95. 50 первых вызовов — разогрев, не учитываются. |
| Почему 12–15 интервью? | Guest et al. (2006): в однородной группе насыщение (новые темы перестают появляться) наступает примерно к 12 интервью. |
| Выборка ведь не случайная? | Да, удобная (convenience) — списка «всех Python-разработчиков» не существует. Случайность есть там, где важно для внутренней валидности: случайное распределение по порядку условий и наборам инструментов. Ограничения обобщаемости названы явно. |
| Почему MCP должен быть быстрее, если первый раз писать сервер дольше? | Возможно, для первого приложения MCP и медленнее — поэтому время для App 1 и App 2 считается отдельно. Выигрыш ожидается при повторном использовании: во втором приложении достаточно подключиться к серверу. |
| Почему H2a — «эквивалентность», а не «разница»? | Модель видит одинаковые имя, описание и схему инструмента; протокол не должен менять её поведение. «Нет значимой разницы» ≠ «одинаково», поэтому проверяем, что 95 % CI разности лежит в пределах ±5 п.п. |
| Что такое McNemar? | Тест для парных бинарных исходов: одна и та же задача решена/не решена в двух условиях (5 и 20 инструментов). |
| Что такое SUS и TAM? | SUS — 10 вопросов об удобстве, балл 0–100, среднее ≈ 68 (Brooke 1996). TAM — воспринимаемая простота и полезность (Davis 1989). |
| Как обеспечена воспроизводимость? | Публикуются код, задачи, трейсы, версии библиотек и моделей, скрипты анализа; план анализа фиксируется до сбора данных. |
| Главные ограничения? | Студенты/джуниоры и простые инструменты, лабораторные условия, быстро меняющиеся библиотеки, синтетические сервисы, две модели. Безопасность MCP и RAG — вне рамок. |
| Критерии хорошего исследования (лекция)? | Systematic — чёткие этапы; logical — гипотезы из пробелов литературы, проверка дедуктивно; empirical — выводы только по измеренным данным; replicable — всё опубликовано. |
