# ПР5 — текст для защиты (читать с телефона)

Здравствуйте. Моя пятая практическая работа — это план и методология исследования. Тема: как подключать инструменты к LLM-агенту на AI-платформе — через протокол MCP или через LangChain.

Сначала коротко, что такое инструмент. Инструмент — это обычная функция, например «получить расписание группы» или «создать заявку». Модель сама её не выполняет. Она видит название, описание и параметры функции и говорит: «вызови вот эту функцию с такими аргументами». Программа выполняет функцию и возвращает результат модели. Модель смотрит на результат и решает, что делать дальше. Этот цикл — подумал, вызвал инструмент, посмотрел результат — называется agent loop.

Подключить инструменты можно двумя способами.

Первый способ — LangChain. Это популярная библиотека на Python для создания агентов, вместе с LangGraph. Мы пишем функцию и ставим над ней декоратор `@tool`. Функция живёт внутри самого агента. Минус в том, что если тот же инструмент нужен в другом приложении, код приходится копировать.

Второй способ — MCP, Model Context Protocol. Это открытый стандарт. Инструмент выносится в отдельный MCP-сервер, а любое приложение подключается к нему через MCP-клиент. Сервер отдаёт инструменты, ресурсы и шаблоны промптов. Связь идёт либо через stdio, то есть как локальный процесс, либо по HTTP. Плюс в том, что инструмент пишется один раз и используется везде. В LangChain MCP-инструменты подгружаются библиотекой `langchain-mcp-adapters`.

Сама модель за агентом может быть облачной, а может быть своей, поднятой через vLLM или Ollama с OpenAI-совместимым API. Для моего исследования это неважно, поэтому модель здесь — просто фон.

Теперь мои исследовательские вопросы. Их четыре.

Первый — про трудозатраты. Если одни и те же три инструмента нужны в двух разных приложениях, быстрее ли подключить их через MCP, чем через обычный `@tool`? Гипотеза: через MCP хотя бы на двадцать пять процентов быстрее.

Второй — про точность. Одинаково ли часто агент выбирает правильный инструмент с правильными аргументами, когда инструменты из MCP и когда они встроенные? И падает ли точность, когда инструментов становится не пять, а двадцать? Гипотеза: MCP и встроенные инструменты дают одинаковую точность, а при двадцати инструментах точность ниже хотя бы на десять процентных пунктов.

Третий — про скорость. Сколько времени добавляет вызов через MCP? Гипотеза: меньше десяти миллисекунд через stdio и меньше тридцати через HTTP. Это меньше двух процентов от одного шага агента.

Четвёртый — про удобство. Насколько разработчикам удобно работать с MCP? Это измеряю стандартным опросником SUS, норма — 68 баллов.

Дизайн исследования — смешанный, в основном количественный. Сначала идут измерения, потом короткие интервью, которые объясняют цифры. По классификации из лекции исследование прикладное, эмпирическое и аналитическое.

Главный эксперимент — с разработчиками. Каждый разработчик делает задание обоими способами: и через MCP, и через `@tool`. Порядок меняется по схеме латинского квадрата, чтобы эффект обучения не исказил результат. Так каждый человек сравнивается сам с собой, и это убирает разницу в опыте между людьми.

Сколько участников. Расчёт мощности для парного теста даёт двадцать четыре разработчика. Набираю двадцать восемь, с запасом на тех, кто выбудет. Для проверки точности нужно сто двадцать тестовых задач, каждая прогоняется три раза. Задержку меряю на тысяче вызовов. Интервью — двенадцать–пятнадцать: по исследованиям, к этому числу новые идеи обычно перестают появляться.

Инструменты сбора данных у меня в приложениях: гайд интервью, анкета SUS и TAM, лист заданий для разработчиков с автоматическими тестами и форма согласия. Перед основным этапом всё проверяется на пилоте.

Анализ. Для времени — парный t-тест или тест Уилкоксона. Для точности — тест Макнемара и доверительные интервалы. Для задержки — медиана и девяносто пятый процентиль. Интервью разбираю тематическим анализом.

Этика. Участие добровольное, есть согласие, данные анонимные, все сервисы тестовые с синтетическими данными, персональные данные не используются.

Ограничения. Один университет, студенты-разработчики вместо опытных инженеров, а библиотеки быстро меняются, поэтому версии фиксирую.

Итог: методология систематичная, логичная, эмпирическая и воспроизводимая. Это ровно те четыре критерия хорошего исследования из лекции. Спасибо, готов ответить на вопросы.
