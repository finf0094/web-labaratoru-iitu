СТРАНИЦА 1 — титул и Abstract

Здравствуйте. Моя пятая работа — план и методология исследования. Тема: как подключать инструменты к LLM-агенту на AI-платформе — через протокол MCP или через LangChain.

СТРАНИЦА 2 — Introduction (что такое инструменты, LangChain и MCP)

Языковая модель сама умеет только писать текст. Чтобы она могла посмотреть расписание или создать заявку, ей дают инструменты. Инструмент — это обычная функция с названием, описанием и параметрами. Модель говорит: «вызови get_timetable для группы SE-2203». Программа выполняет функцию и возвращает результат, а модель решает, что делать дальше. Цикл «подумал — вызвал инструмент — посмотрел результат» называется agent loop.

Подключить инструменты можно двумя способами. Первый — LangChain, популярная библиотека для создания агентов на Python. Пишем функцию с декоратором tool, и она живёт внутри агента. Это просто, но для другого приложения код приходится копировать.

Второй способ — MCP, Model Context Protocol, открытый стандарт. Инструмент выносится в отдельный MCP-сервер, а любое приложение подключается к нему через клиент — по stdio или HTTP. Инструмент пишется один раз и используется везде. В LangChain такие инструменты подключаются библиотекой langchain-mcp-adapters. Сама модель может быть облачной или своей — через vLLM или Ollama.

СТРАНИЦА 3 — таблица с исследовательскими вопросами

Почему это нужно исследовать. Про MCP говорят: «напиши инструмент один раз — и используй в любом приложении». Но это пока только обещание: никто не проверял на цифрах, экономит ли это время, не путается ли агент и не тормозит ли система. Это пробел, который я закрываю.

В таблице четыре вопроса.
Первый — про время разработчика. Три инструмента — расписание, заявка и поиск документов — нужны в двух приложениях. Я сравниваю, сколько времени уйдёт через MCP и через обычный tool. Ожидаю, что MCP быстрее хотя бы на четверть, потому что второй раз код писать не нужно.
Второй — про точность. Не станет ли агент чаще выбирать не тот инструмент через MCP? Ожидаю, что разницы не будет. А когда инструментов не пять, а двадцать, агент будет ошибаться чаще, потому что ему сложнее выбрать.
Третий — про скорость. Ожидаю, что MCP добавляет меньше десяти миллисекунд — это незаметно на фоне ответа модели.
Четвёртый — про удобство. Меряю анкетой SUS, ожидаю не ниже шестидесяти восьми баллов — это средний уровень.

По расчёту мощности нужно двадцать четыре разработчика, набираю двадцать восемь с запасом. Для проверки точности — сто двадцать тестовых задач, каждая по три прогона. Для скорости — тысяча замеров. Интервью — двенадцать–пятнадцать: примерно к этому числу новые темы перестают появляться.

СТРАНИЦА 6 — латинский квадрат и таблица методов сбора данных

Каждый разработчик делает задание обоими способами, поэтому сравнивается сам с собой. Порядок меняется по латинскому квадрату, а наборы инструментов разные, но одинаковые по сложности — так не мешает эффект обучения.

Задание считается выполненным, когда проходят автоматические тесты, поэтому оценка объективная. Все вызовы инструментов пишутся в лог. Ещё используются анкеты SUS и TAM, метод «думай вслух» и интервью.

СТРАНИЦА 9 — анализ данных и итог

Время анализирую парным тестом, точность — тестом Макнемара, скорость — медианой, интервью — тематическим анализом. Ограничения: один университет, студенты вместо опытных инженеров, библиотеки быстро меняются, поэтому версии фиксирую.

Итог: методология систематичная, логичная, эмпирическая и воспроизводимая — это четыре критерия хорошего исследования из лекции. Результат поможет решить, стоит ли подключать все инструменты платформы через MCP.
