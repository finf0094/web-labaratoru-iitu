# ПР5 — текст для защиты (~15 минут)

**[0:00 — 1. Вступление]**

Здравствуйте. Меня зовут ____, группа ____. Я представляю пятую практическую работу по курсу «Методология исследований». Её задача — превратить план исследования в подробную методологию, по которой другой исследователь смог бы повторить мою работу.

Моя тема: как подключать инструменты к LLM-агенту на AI-платформе — через протокол MCP или через библиотеку LangChain.

Сначала я объясню, что такое инструменты, агент, MCP и LangChain, потому что без этого непонятно, что именно я исследую. Затем расскажу исследовательские вопросы и гипотезы, дизайн исследования, выборку, методы и инструменты сбора данных, процесс сбора, анализ, этику и ограничения. В конце подведу итог.

**[1:00 — 2. Что такое AI-платформа и агент]**

Сегодня большие языковые модели, например GPT, Claude, Llama или Qwen, используются не только как чат-боты. Их делают «мозгом» программ, которые называются агентами. Агент не просто отвечает текстом, а выполняет задачи: смотрит расписание, создаёт заявку, ищет документ.

Сама модель умеет только генерировать текст. Она не может сама зайти в базу данных или отправить запрос в систему университета. Для этого нужны инструменты.

Инструмент — это обычная функция в программе. Например, «получить расписание группы», «создать заявку в поддержку», «найти документ». У каждого инструмента есть название, описание на естественном языке и параметры в формате JSON-схемы.

Работает это так. Модель получает вопрос пользователя и список доступных инструментов. Если для ответа нужен инструмент, модель говорит программе: «вызови get_timetable с параметром group равным SE-2203». Программа выполняет функцию и возвращает результат модели. Модель смотрит на результат и решает, что делать дальше: вызвать ещё один инструмент или уже ответить пользователю. Этот механизм называется function calling, или tool calling.

Цикл «подумал — вызвал инструмент — посмотрел результат — снова подумал» называется agent loop, агентный цикл. Он описан в известной работе ReAct, где рассуждения модели чередуются с действиями.

AI-платформа — это система, которая объединяет модель, агентный цикл, инструменты и доступ к данным организации, чтобы разные команды могли быстро делать своих AI-ассистентов.

**[3:00 — 3. Откуда берётся модель]**

Пару слов о том, откуда берётся сама модель. Есть два варианта. Первый — облачный API, например OpenAI или Anthropic: отправляем запрос и получаем ответ. Второй — поднять модель на своём сервере. Для этого используют vLLM — это сервер, который эффективно запускает модели на GPU и отдаёт API, совместимый с OpenAI. Для локальной разработки есть Ollama, она запускает модели одной командой даже на ноутбуке.

Для моего исследования важно, что у агента один и тот же интерфейс, OpenAI-совместимый API. Поэтому модель можно заменить, не меняя код инструментов. Модель в моей работе — фон, а исследую я именно слой инструментов.

**[3:40 — 4. Два способа подключить инструменты]**

Теперь главное — два способа подключения инструментов, которые я сравниваю.

Первый способ — LangChain. LangChain и LangGraph — популярные библиотеки на Python для создания агентов. LangChain даёт готовые блоки: модели, промпты, инструменты, цепочки. LangGraph позволяет описать агента как граф шагов. Чтобы сделать инструмент, мы пишем обычную функцию и ставим над ней декоратор `@tool`. Функция становится инструментом и живёт внутри процесса агента.

Это очень просто, но есть минус. Если тот же инструмент нужен в другом приложении — например, в веб-чате на FastAPI, а не в консольном агенте, — код приходится копировать или упаковывать заново. Чем больше приложений, тем больше копий и тем сложнее их поддерживать.

Второй способ — MCP, Model Context Protocol. Это открытый стандарт, его выпустили в ноябре 2024 года, а сейчас он развивается в Agentic AI Foundation при Linux Foundation. Идея похожа на USB для AI: один стандартный разъём для всех инструментов.

В MCP есть три роли. Host — это приложение, например AI-платформа или чат. Внутри него работает MCP-клиент. Клиент подключается к MCP-серверу, а сервер предоставляет инструменты, ресурсы, то есть данные только для чтения, и шаблоны промптов. Клиент и сервер общаются сообщениями JSON-RPC через транспорт. Транспортов два: stdio, когда сервер запущен как локальный процесс, и streamable HTTP, когда сервер работает по сети.

Главный плюс: инструмент пишется один раз как MCP-сервер, и подключить его может любое MCP-совместимое приложение. В LangChain это делает библиотека `langchain-mcp-adapters` — она загружает инструменты с MCP-сервера и превращает их в обычные инструменты LangChain.

Технический стек моего исследования: официальный Python SDK для MCP, библиотеки langchain, langgraph и langchain-mcp-adapters, FastAPI для тестовых сервисов с синтетическими данными и pytest для автоматических тестов.

**[6:00 — 5. Проблема и пробелы в литературе]**

Почему это нужно исследовать? В обзоре литературы я нашёл три пробела.

Первый: MCP продвигают под лозунгом «напиши инструмент один раз и используй везде», но эту выгоду никто не измерял. Это утверждение, а не доказанный факт.

Второй: есть бенчмарки, которые проверяют, насколько хорошо модели используют MCP-серверы. Но нет сравнения, влияет ли сам способ подключения на точность агента. Известно и то, что на реалистичных многошаговых задачах агенты часто ошибаются.

Третий: нет данных о том, насколько MCP замедляет работу и насколько он удобен для обычных разработчиков.

**[7:00 — 6. Исследовательские вопросы и гипотезы]**

Отсюда четыре исследовательских вопроса. Каждый конкретный и измеримый.

Первый вопрос — про трудозатраты. Если одни и те же три инструмента нужно использовать в двух разных приложениях, быстрее ли подключить их через MCP, чем через `@tool`? Гипотеза H1: общее время до прохождения всех тестов в обоих приложениях через MCP минимум на двадцать пять процентов меньше. Меряю минуты, строки кода и число неудачных запусков тестов.

Второй вопрос — про точность. Одинаково ли часто агент выбирает правильный инструмент с правильными аргументами, когда инструменты из MCP и когда они встроенные? И как меняется точность, если инструментов не пять, а двадцать? Гипотеза H2a: способы эквивалентны, разница не больше пяти процентных пунктов. Гипотеза H2b: при двадцати инструментах точность ниже хотя бы на десять пунктов, потому что модели сложнее выбрать нужный.

Третий вопрос — про скорость. Сколько времени добавляет вызов через MCP по сравнению с обычной функцией? Гипотеза H3: меньше десяти миллисекунд через stdio и меньше тридцати через HTTP, то есть меньше двух процентов от одного шага агента.

Четвёртый вопрос — про удобство. Как разработчики оценивают работу с MCP? Гипотеза H4: оценка по опроснику SUS не ниже шестидесяти восьми баллов — это среднее значение по многим системам — и не ниже, чем у обычных инструментов.

**[8:40 — 7. Дизайн исследования]**

Дизайн — смешанные методы, в основном количественные. Точнее, это объяснительный последовательный дизайн: сначала количественные измерения, потом качественная часть, которая объясняет цифры. Вся работа строится в рамках Design Science Research: я создаю небольшой артефакт — три инструмента в двух вариантах и систему для их оценки — и оцениваю его.

По классификации из лекции исследование прикладное, потому что решает практическую задачу; эмпирическое, потому что основано на измерениях; аналитическое, потому что сравнивает существующие технологии; и ориентировано на принятие решений — помогает команде платформы выбрать способ подключения инструментов. Подходы: экспериментальный, потому что я меняю способ подключения и число инструментов; симуляционный, потому что агенты работают с тестовыми сервисами; и инференциальный — опрос участников.

Почему в основном количественный? Первые три вопроса — о причине и следствии: уменьшает ли MCP время, меняет ли точность, добавляет ли задержку. На такие вопросы отвечают контролируемые сравнения и статистика. А качественная часть нужна, потому что цифры не объясняют, почему так получилось.

Исследование состоит из пяти частей: эксперимент с разработчиками, набор тестовых задач для агента, замер задержки, анкеты и интервью.

**[10:00 — 8. Выборка]**

Эксперимент с разработчиками. Участники — те, кто умеет писать на Python: студенты старших курсов, магистранты и junior-разработчики. Используется выборка по доступности со входным тестом на Python. Случайность вводится там, где она важна, — при распределении участников по группам.

Дизайн внутригрупповой: каждый участник выполняет задание обоими способами. Это важно, потому что уровень программистов сильно отличается, а так каждый сравнивается сам с собой. Чтобы не влиял эффект обучения, используется латинский квадрат: четыре группы с разным порядком способов и разными наборами инструментов. Набор A — расписание, создание заявки и поиск документов. Набор B — расписание экзаменов, бронирование аудитории и поиск новостей. Они одинаковые по сложности, поэтому никто не делает один и тот же инструмент дважды.

Сколько нужно людей? Я сделал расчёт мощности для парного t-теста: уровень значимости 0,05, мощность 0,8. При среднем эффекте d = 0,6 нужно двадцать четыре человека, при d = 0,5 — тридцать четыре. Я планирую двадцать четыре, это кратно четырём для латинского квадрата, и набираю двадцать восемь с запасом на выбывание.

Набор задач для агента — сто двадцать задач четырёх типов: один инструмент, два инструмента подряд, извлечение аргументов из текста и задачи, где инструмент не нужен. Число получено расчётом для теста Макнемара: чтобы заметить падение точности с девяноста до восьмидесяти процентов, нужно сто восемь задач, плюс запас. Каждая задача прогоняется три раза в четырёх условиях на двух моделях — всего две тысячи восемьсот восемьдесят запусков агента.

Задержку меряю на тысяче вызовов в каждом режиме после пятидесяти разогревочных. Интервью — двенадцать–пятнадцать: исследования показывают, что примерно к двенадцати интервью новые темы перестают появляться. Все эти числа считает мой скрипт `sample_size.py`.

**[11:40 — 9. Методы и инструменты сбора данных]**

Методы сбора данных такие. Первый — эксперимент с замером времени. Задание считается выполненным, когда проходят автоматические тесты pytest. Так «готово» определяется объективно, а не по мнению участника. Второй — прогоны агента с полной записью: каждый вызов инструмента, его аргументы и результат пишутся в лог. Третий — микробенчмарк задержки. Четвёртый — анкеты SUS и TAM. Пятый — метод «думай вслух», когда участник проговаривает свои действия. Шестой — короткие интервью после сессии.

Инструменты сбора данных лежат в приложениях: лист заданий для разработчиков с тестами, спецификация тестовых задач, анкета, гайд интервью и форма информированного согласия.

Перед основным этапом проводится пилот: два добровольца проходят всю сессию, а двадцать задач прогоняются полностью. Так я проверяю, понятны ли инструкции, хватает ли сорока минут на задание и одинаковы ли по сложности наборы A и B. Данные пилота в анализ не входят.

**[12:40 — 10. Процесс сбора и этика]**

Процесс по времени: в ноябре — одобрение и подготовка инструментов, в декабре — пилот, в декабре и январе — прогоны агента и замеры задержки, в феврале и марте — эксперимент с разработчиками, в марте и апреле — анализ. Одна сессия длится около двух часов: два задания по сорок минут, анкеты и интервью.

Этика. Участие добровольное, можно выйти в любой момент, это не влияет на оценки. Каждый подписывает информированное согласие. В данных используются только коды участников, а записи удаляются после расшифровки. Данные хранятся на защищённом университетском диске и обрабатываются по закону Республики Казахстан о персональных данных. Все инструменты работают только с тестовыми сервисами и синтетическими данными, реальные системы университета не затрагиваются.

**[13:30 — 11. Анализ данных]**

Анализ. Для трудозатрат — парный t-тест или тест Уилкоксона, если данные не нормальные, и размер эффекта. Отдельно смотрю время для первого и второго приложения: возможно, MCP медленнее в первый раз, но быстрее при повторном использовании. Для точности — бутстреп-интервал разницы и тест Макнемара. Для задержки — медиана и девяносто пятый процентиль. Для удобства — баллы SUS и TAM. Интервью разбираются тематическим анализом по Браун и Кларк, а потом количественные и качественные результаты сводятся в одну таблицу.

**[14:10 — 12. Ограничения и вывод]**

Ограничения: участники в основном студенты, а не опытные команды; только Python и простые инструменты; библиотеки быстро меняются, поэтому я фиксирую их версии; один университет.

Итог. Методология систематичная — у неё чёткие этапы; логичная — гипотезы следуют из литературы; эмпирическая — выводы основаны на измерениях; воспроизводимая — все задачи, код и данные публикуются. Это четыре критерия хорошего исследования из лекции. Результат поможет команде AI-платформы решить, стоит ли подключать все инструменты через MCP.
