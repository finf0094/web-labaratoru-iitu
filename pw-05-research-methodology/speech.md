# ПР5 — текст для защиты (~7 минут)

**[0:00 — Вступление]**
Здравствуйте. Моя пятая работа — план и методология исследования. Тема: как подключать инструменты к LLM-агенту на AI-платформе — через протокол MCP или через LangChain.

**[0:20 — Основные понятия]**
Языковая модель сама умеет только писать текст. Чтобы она могла посмотреть расписание или создать заявку, ей дают инструменты. Инструмент — это обычная функция с названием, описанием и параметрами. Модель говорит: «вызови get_timetable для группы SE-2203». Программа выполняет функцию и возвращает результат, а модель решает, что делать дальше. Цикл «подумал — вызвал инструмент — посмотрел результат» называется agent loop.

Сама модель может быть облачной, например OpenAI, или своей — поднятой через vLLM или Ollama с OpenAI-совместимым API. Для моей работы это неважно: я исследую слой инструментов.

**[1:20 — Два способа подключения]**
Первый способ — LangChain, популярная библиотека для создания агентов на Python. Пишем функцию с декоратором `@tool`, и она живёт внутри агента. Это просто, но для другого приложения код приходится копировать.

Второй способ — MCP, Model Context Protocol, открытый стандарт с 2024 года. Инструмент выносится в отдельный MCP-сервер, а любое приложение подключается к нему через клиент — по stdio или HTTP. Инструмент пишется один раз и используется везде. В LangChain такие инструменты подключаются библиотекой `langchain-mcp-adapters`.

**[2:20 — Пробел и вопросы]**
MCP обещает «напиши один раз, используй везде», но это никто не измерял. Поэтому у меня четыре вопроса.
Первый — трудозатраты: быстрее ли подключить одни и те же три инструмента к двум приложениям через MCP? Гипотеза: минимум на двадцать пять процентов.
Второй — точность: одинаково ли часто агент выбирает правильный инструмент через MCP и напрямую, и падает ли точность при двадцати инструментах вместо пяти?
Третий — скорость: MCP добавляет меньше десяти миллисекунд на вызов.
Четвёртый — удобство по опроснику SUS, норма — шестьдесят восемь баллов.

**[3:30 — Дизайн и выборка]**
Дизайн смешанный, в основном количественный: сначала измерения, потом интервью, которые объясняют цифры. По лекции исследование прикладное, эмпирическое и аналитическое.

Главный эксперимент такой: каждый разработчик делает задание обоими способами, поэтому сравнивается сам с собой. Порядок меняется по латинскому квадрату, а наборы инструментов разные, но одинаковые по сложности, чтобы не мешал эффект обучения.

Расчёт мощности даёт двадцать четыре разработчика, набираю двадцать восемь с запасом. Для точности — сто двадцать тестовых задач по три прогона, для скорости — тысяча замеров, интервью — двенадцать–пятнадцать.

**[4:50 — Сбор данных и анализ]**
Задание считается выполненным, когда проходят автоматические тесты, поэтому оценка объективная. Все вызовы инструментов пишутся в лог. Есть анкеты SUS и TAM, метод «думай вслух» и интервью; всё это в приложениях. Перед основным этапом проводится пилот на двух участниках.

Время анализирую парным тестом, точность — тестом Макнемара, скорость — медианой, интервью — тематическим анализом.

**[5:50 — Этика и ограничения]**
Участие добровольное, есть согласие, данные анонимные, сервисы тестовые, персональных данных нет. Ограничения: один университет, студенты вместо опытных инженеров, библиотеки быстро меняются, поэтому версии фиксирую.

**[6:20 — Вывод]**
Методология систематичная, логичная, эмпирическая и воспроизводимая — это четыре критерия хорошего исследования из лекции. Результат поможет решить, стоит ли подключать все инструменты платформы через MCP. Спасибо, готов ответить на вопросы.
