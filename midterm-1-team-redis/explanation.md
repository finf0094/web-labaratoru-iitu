## 1. О чём статья в трёх предложениях

Обычно говорят: «поставь Redis перед базой данных, и API станет в несколько раз быстрее». Мы это **проверили экспериментом**: сравнили Spring Boot API с PostgreSQL без кэша и с кэшем Redis при 100, 500 и 1000 одновременных пользователях.

**Итог:**

* Redis убрал 91% запросов к базе и сократил «хвост» задержки (p99) на 32–61%.
* Средняя скорость и пропускная способность при этом **не выросли**, а на равномерной нагрузке пропускная способность даже упала на 22–34%.
* Причина: база тратила только 32% процессорного времени на запрос, а путь через кэш добавил работу самой Java-машине.

## 2. Термины простыми словами

| Термин | Простое объяснение |
|---|---|
| **REST API** | Сервис, который отвечает на HTTP-запросы. У нас один запрос: `GET /api/products/{id}`, он возвращает карточку товара. |
| **Spring Boot** | Популярный Java-фреймворк для написания таких сервисов. |
| **PostgreSQL** | Реляционная база данных, где лежат товары, категории и отзывы. |
| **Redis** | Быстрое хранилище «ключ–значение» в оперативной памяти. Его ставят как кэш. |
| **Кэш (cache)** | Копия часто нужных данных в быстрой памяти, чтобы не ходить каждый раз в базу. |
| **Cache-aside** | Схема работы кэша. Сначала смотрим в Redis. Если данные есть (**hit**), сразу отдаём. Если нет (**miss**), идём в базу, отдаём ответ и кладём его в Redis. |
| **TTL** | Время жизни записи в кэше. У нас 300 секунд. |
| **Hit ratio** | Доля запросов, на которые ответил кэш. 91% значит, что 9 из 10 запросов не пошли в базу. |
| **LRU-вытеснение (allkeys-lru)** | Когда память Redis (32 МБ) заканчивается, удаляются ключи, которые дольше всего не использовались. |
| **Тайм-аут Redis (100 мс / 1 с)** | Сколько сервис ждёт ответа от Redis. Если не дождался, считает это ошибкой и идёт в базу (fallback). |
| **B, R100, R1000** | Три конфигурации: B — без кэша (контроль), R100 — Redis с тайм-аутом 100 мс, R1000 — Redis с тайм-аутом 1 с. |
| **VU (virtual user)** | Виртуальный пользователь в генераторе нагрузки k6. |
| **Закрытая модель, zero think time** | Каждый VU отправляет следующий запрос сразу после ответа на предыдущий. Поэтому в системе всегда N запросов. |
| **Hot / uniform нагрузка** | Hot: 90% запросов идут к 1000 популярным товарам, как в реальной жизни. Uniform: все 100 000 товаров одинаково вероятны. |
| **Задержка (latency): mean, p95, p99** | Время ответа. Mean — среднее. p99 — 99% запросов быстрее этого значения, то есть это «хвост», самые медленные запросы. |
| **Пропускная способность (throughput)** | Сколько успешных ответов в секунду обрабатывает сервис. |
| **vCPU** | Виртуальное ядро процессора. Весь тестируемый сервис работал на **одном** ядре (через `taskset`). |
| **JIT-компиляция и прогрев (warm-up)** | Java сначала исполняет код медленно, а потом компилирует «горячие» методы в машинный код. Мерить нужно только после того, как компиляция закончилась. |
| **Очередь JIT (jcmd)** | Сколько методов ещё ждут компиляции. Мы прогревали сервис, пока в очереди не осталось 10 методов или меньше. |
| **pg_prewarm** | Заранее загружает таблицы PostgreSQL в память, чтобы все прогоны стартовали одинаково. |
| **Парный блок** | В одном блоке при одинаковых условиях измеряются все конфигурации, в случайном порядке. Так фоновые колебания машины не дают преимущества никому. |
| **Бутстрэп и доверительный интервал (CI)** | Много раз случайно пересобираем 5 прогонов и смотрим разброс. Если интервал отношения включает 1, разницы достоверно нет. |
| **Поправка Бонферрони** | Проверяли 2 гипотезы, поэтому вместо 95% интервалов взяли 97,5%. |
| **Коэффициент вариации (CV)** | Разброс относительно среднего. У одинаковых прогонов он был 13–46%. |
| **Закон Литтла: N = X · R** | Число запросов в системе = пропускная способность × среднее время ответа. Мы им проверяли, что измерения согласованы. |
| **Закон Амдала: ускорение ≤ 1 / (1 − f)** | Если убрать долю f работы, быстрее чем в 1/(1−f) раз не станет. У нас f ≈ 0,32, значит максимум около 1,47×. |
| **Context switch (переключение контекста)** | Процессор переключается между потоками. Каждый вызов Redis передаётся сетевому потоку клиента Lettuce и обратно, а это лишние переключения. |

## 3. Как устроен эксперимент

* **Приложение** написано специально для исследования: Java 21, Spring Boot 3.5.6, Tomcat с 200 потоками, пул HikariCP на 20 соединений с базой, heap 512 МБ.
* **Данные** синтетические: 100 категорий, 100 000 товаров, 500 000 отзывов (99 МБ). Персональных данных нет.
* **Машина:** 2 vCPU (Intel Xeon 2,1 ГГц), 7,8 ГБ RAM, Ubuntu 24.04. На vCPU 0 работали k6 и скрипт-«дирижёр», на vCPU 1 — Spring Boot, PostgreSQL и Redis.
* **Один прогон:**
  1. Перезапуск JVM, очистка Redis, сброс статистики, pg_prewarm.
  2. Прогрев пачками по 10 с с паузами 3 с, пока очередь JIT не опустеет.
  3. Измерение 30 с.
  4. Остывание 5 с.
* **План:** 15 блоков × 3 конфигурации на hot и 15 блоков × 2 конфигурации на uniform. Всего **75 прогонов**, по 5 повторов в каждой ячейке.
* **Каждый ответ проверялся:** код 200, правильный id, имя товара и 5 отзывов.
* **Почему выбросили первую серию (51 прогон):** при постоянной нагрузке компилятору JIT не хватало процессора. В очереди висело около 600 методов, а после компиляции та же JVM работала в 2,5 раза быстрее. Значит, мерили недогретую Java. Поэтому придумали прогрев «пачками».

**Гипотезы (из плана исследования)** для главного условия (hot, 1000 VU):

* H1: Redis снижает среднюю задержку минимум на 60%;
* H2: Redis повышает пропускную способность минимум в 3 раза.

**Обе не подтвердились.**

## 5. Почему кэш не ускорил (главная мысль защиты)

1. **База была не главной тратой.** Запрос по первичному ключу с индексом дешёвый: 32% CPU. Остальные 68% — это Tomcat, разбор HTTP, преобразование объектов и JSON. Их кэш не убирает.
2. **Попадание в кэш тоже не бесплатное.** Нужно передать команду сетевому потоку Lettuce и обратно, а потом разобрать JSON из Redis и снова собрать JSON ответа. Это съело почти всю экономию.
3. **Всё на одном ядре.** Сэкономленное на базе процессорное время тут же тратится JVM, потому что ядро общее.
4. **Закрытая модель.** При фиксированном числе пользователей задержка = N / пропускная способность. Поэтому снизить задержку на 60% — это то же самое, что поднять пропускную способность в 2,5 раза. Обе гипотезы падают по одной причине.
5. **Где кэш всё-таки помог:**
   * **хвост задержки:** попадания в кэш обходят очередь к 20 соединениям базы;
   * **нагрузка на базу:** минус 90% SQL. Это важно, если одна база обслуживает много копий приложения.

**Практические советы из статьи:**

* до внедрения Redis измерьте долю базы в стоимости запроса и локальность ключей;
* тайм-аут клиента Redis выбирайте по хвосту задержки под пиковой нагрузкой, а не «на глаз» (100 мс оказалось мало);
* JVM прогревайте и меряйте много раз.

### 1. Понятия: научная статья, тезисы, отчёт о НИР, аннотация, доклад

* **Научная статья** — публикация в журнале с новым результатом: задача, метод, данные, результаты, выводы и ссылки. Проходит рецензирование. *Пример:* наша статья про Redis (12 страниц).

* **Доклад** — устное выступление с результатами на конференции или семинаре, обычно 7–15 минут со слайдами.

* **Цель:** количественно оценить влияние Redis cache-aside на Spring Boot API с PostgreSQL под высокой нагрузкой и объяснить эффект измерениями по компонентам.

  4. разработать протокол прогрева;
  5. провести 75 прогонов;

## 8. Возможные вопросы преподавателя

**— Почему гипотезы не подтвердились, это ведь плохо?**
Нет. Отрицательный результат тоже результат. Мы показали, **почему** так: база занимала только 32% CPU, и по закону Амдала ускорение не может быть больше примерно 1,47×. Значит, ускорение в 3 раза было невозможно в такой конфигурации.

**— Зачем один vCPU?**
Чтобы смоделировать маленький облачный сервер и чтобы генератор нагрузки не мешал сервису. Это ограничение мы честно указали: на нескольких ядрах или с базой на отдельном сервере результат может быть другим.

**— Зачем R1000, если в плане был только R100?**
Пилот показал частые тайм-ауты Redis при 100 мс под нагрузкой. R1000 добавили **до** основного сбора данных, это сказано в статье.

**— Почему первую серию из 51 прогона выбросили, это не подгонка?**
Нет. Диагностика jcmd показала, что JVM не догрета: около 600 методов в очереди JIT, а после компиляции скорость в 2,5 раза выше. Данные этой серии не удалены, они сохранены в дополнительных материалах.

**— Почему средние на графике так сильно «прыгают»?**
У Java большой разброс между запусками JVM (CV 13–46%). Поэтому нужны повторы и доверительные интервалы, а не один замер. Об этом пишут Georges и др. (2007).

**— Что значит «доверительный интервал включает 1»?**
Что отношение «кэш / без кэша» может быть и больше, и меньше единицы. Значит, достоверной разницы нет.

**— Так Redis не нужен?**
Нужен, но не для ускорения простого запроса на одном ядре. Он полезен, когда:

* запрос к базе дорогой или база на другом сервере;
* важен хвост задержки;
* нужно разгрузить общую базу.

Кэш убрал 90% SQL-запросов, и это реальная польза.

**— Почему на uniform стало хуже?**
Рабочий набор (56 МБ) больше памяти Redis (32 МБ). Hit ratio всего 50%, Redis вытеснил 241 770 ключей, и каждый промах платит трижды: Redis, SQL и запись в Redis.

**— Какой вклад каждого автора?**
Работа командная, три автора, автор для переписки — Serik Zholdygaliev. *(Перед защитой договоритесь между собой, кто какую часть рассказывает и кто что делал: код, эксперимент, текст.)*

**— Где исходники рисунков?**
В архиве `MT1_sources.zip`, разделы S1–S7: SVG диаграмм, Java-код, скрипт k6, сырые данные всех прогонов, скрипты графиков.
